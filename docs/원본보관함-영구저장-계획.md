# 원본 보관함 영구 저장 계획

> 작성 2026-07-28. 대상: `web/src/cache.ts`(IndexedDB 보관함), `web/src/App.tsx`.
> 목표: **원본 보관함(아트웍 + 섹션)이 절대 유실되지 않게 한다.**

## 1. 지금 구조와 유실 위험

원본 보관함은 현재 **브라우저 IndexedDB**(`artwork-compare-cache` DB의
`artworks`/`sections` 스토어)에만 저장된다. 서버로 가지 않는다.

IndexedDB는 다음 상황에서 **통째로 또는 일부가 사라질 수 있다**:

| 위험 | 설명 | 영향 |
|---|---|---|
| 저장소 압박 시 자동 삭제 | 브라우저가 디스크가 부족하면 "best-effort" 오리진 데이터를 예고 없이 지운다 | 아트웍 원본(수 MB×N)이라 특히 취약 |
| 브라우저 데이터 삭제 | 사용자/회사 정책이 "인터넷 사용 기록·쿠키·사이트 데이터 삭제" 실행 | 전량 소실 |
| 시크릿/게스트 창 | 세션 종료 시 전부 폐기 | 전량 소실 |
| 다른 기기·다른 브라우저 | IndexedDB는 브라우저·프로필 로컬 | 애초에 공유 안 됨 |
| 도메인 변경 | 배포 URL이 바뀌면 오리진이 달라 접근 불가 | 접근 불가 |

즉 **"영구·유실 금지"를 IndexedDB만으로는 보장할 수 없다.** 로컬은 편의 캐시로
두고, 원본은 별도의 신뢰 저장소에 두는 이중화가 필요하다.

## 2. 이미 적용한 1차 방어 (이번 커밋)

`navigator.storage.persist()`로 저장소를 **`persistent`로 승격 요청**한다.
승격되면 사용자가 명시적으로 지우기 전까지 브라우저가 자동 삭제하지 않는다.

- `cache.ts`: `requestPersistentStorage()`, `storageEstimate()` 추가
- `App.tsx`: 앱 최초 로드 시 `requestPersistentStorage()` 호출

한계: 위 표의 **자동 삭제**만 막는다. 수동 삭제·다른 기기·시크릿 창은 못 막는다.
근본 해결은 **서버 보관(3절)**.

## 3. 근본 해결안 — 서버 보관 (택1)

핵심 판단: **"어디서든 안 잃는다"를 원하면 원본을 서버에 둬야 한다.**
이미 피드백 수집용으로 **Vercel Functions + Blob**(`print-compare-feedback`)을 쓰고
있으므로, 같은 스택을 확장하는 게 비용·운영 면에서 가장 매끄럽다.

### 안 A — 로그인 없는 공용 보관함 (가장 빠름)
- 아트웍/섹션을 Blob(또는 KV)에 저장하는 `GET/PUT /api/library` 추가.
- 접근 통제는 지금 관리자 화면처럼 **단일 공유 비밀번호 게이트**.
- 로컬 IndexedDB는 캐시로 유지, 서버가 정본(source of truth).
- 장점: 로그인 UI 불필요, 팀 전체가 같은 보관함 공유.
- 단점: 누가 올렸는지 구분 없음, 비번 하나가 모든 접근 권한.

### 안 B — 사용자 로그인 도입 (요청하신 "로그인 고려")
- 사용자별 계정 → 사용자별(또는 팀별) 보관함 네임스페이스.
- 인증 옵션(가벼운 순):
  1. **매직링크/OTP 이메일** — 비밀번호 저장 없음, 사내 메일로 충분.
  2. **Vercel 마켓플레이스 Clerk/Auth0** — 표준 로그인, 설정 빠름.
  3. **회사 SSO(구글 워크스페이스 등)** — 가장 안전하나 도입 비용 큼.
- 저장: 안 A와 동일한 Blob/KV에 `userId` 또는 `teamId`로 키 분리.
- 장점: 기기 무관 접근, 감사 추적(누가 언제), 권한 분리.
- 단점: 인증 인프라·개인정보 처리 방침 필요, 구현량 최다.

### 안 C — 로컬 백업/복원 (서버 없이 최소 안전망)
- 보관함 전체를 **zip으로 내보내기/가져오기** 버튼 추가.
- 서버 없이도 사용자가 주기적으로 백업 파일을 남길 수 있음.
- 장점: 인프라 0, 즉시 구현.
- 단점: 수동 의존(백업을 안 하면 소용없음). A/B의 보완재로 적합.

### 안 A 구현 메모 (v2 — 2026-07-29 증분 동기화로 전환)
v1은 보관함 전체를 base64 JSON **한 덩어리**로 올렸다. 폴더·이미지가 늘면
문자열 하나가 수백 MB가 돼 탭이 죽고, 중간에 끊기면 처음부터 다시였다.
v2는 **매니페스트 + 파일 단위**로 나눈다.

- 저장 구조
  - `library/f/<sha256>` — 원본 파일 1개 = blob 1개. 내용 주소라 같은 파일은
    한 번만 올라가고 재업로드는 덮어쓰기(멱등).
  - `library/manifest.json` — 폴더 트리 + 파일 목록(메타데이터만). 랜덤 접미사로
    URL 추측 불가, 최근 5개 이력만 보관.
- 업로드: `POST {action:"listfiles", password}`로 서버에 이미 있는 해시를 받아
  **없는 것만** 올린다 → 두 번째 백업부터는 바뀐 파일만 전송. 함수는 토큰만
  발급하므로 body 크기 제한(~4.5MB)과 무관.
- 불러오기: 매니페스트를 받아 폴더 트리를 반영하고, **로컬에 없는 해시만**
  내려받아 병합한다(로컬 유지 + 서버 항목 추가).
- 메모리: 한 번에 다루는 최대치가 "가장 큰 파일 1개"로 고정된다.
- 보안: blob은 public이지만 경로를 모르면 접근 불가. 파일 경로는 콘텐츠
  해시라 파일을 이미 가진 사람만 알 수 있고, 목록을 주는 listfiles/geturl은
  비번 게이트다. 라벨 원본이 담기므로 URL 관리가 곧 접근 통제.
- 구버전 호환: 서버에 v1 백업(`library/backup*`)만 있으면 불러오기가 그것을
  읽어 되살린다(1회성 이행 경로). geturl 액션도 유지.
- env(공유 백엔드): `ADMIN_PASSWORD`(기존), `BLOB_READ_WRITE_TOKEN`(Blob 자동).

## 4-2. 규모 한계 실측 (2026-07-29, Apple Silicon + Chrome)

`cd web && npm run bench:library` (`web/tools/library-bench.mjs`) — 실제 크롬의
IndexedDB에 넣고 잰 값이다.

| 항목 | 측정치 | 해석 |
|---|---|---|
| 원본 저장 | 1.1ms/건 (50KB 기준) | 1000개 넣는 데 1.1초 — 개수는 병목 아님 |
| `listArtworks()` 1000건 | 20ms | 화면 새로고침마다 호출해도 체감 없음 |
| `listArtworkHashes()` | 4ms | 동기화가 쓰는 경로는 훨씬 가벼움 |
| `exportManifest()` 1000건 | 14ms → 0.1MB JSON | 매니페스트는 파일 수만큼만 커짐 |
| 큰 파일 저장/읽기 | 1.4GB/s · 3.1GB/s | 5MB 라벨 20장이 0.1초 미만 |
| 폴더 200개 생성/조회 | 115ms / 1ms | 폴더 수도 병목 아님 |
| **저장소 할당량** | **약 3GB** (측정 환경) | **여기가 진짜 한계** |

결론: **개수가 아니라 용량이 한계**다. 10MB짜리 라벨 기준 약 300장이 들어가면
할당량이 찬다(할당량은 브라우저가 남은 디스크에 비례해 정하므로 기기마다 다름).

대응으로 넣은 것:
- 사이드바 하단에 **사용량/한도 표시**, 80% 초과나 persist 미적용이면 강조.
- 동기화를 파일 단위로 바꿔 **백업 자체가 메모리를 터뜨리지 않게** 했다
  (v1이었다면 3GB 보관함 = 4GB짜리 문자열 하나 → 불가능).
- 폴더 트리는 접힌 폴더의 내용을 렌더하지 않고, 트리 영역만 스크롤한다.

더 늘려야 하면: 원본을 서버에만 두고 로컬은 최근 것만 캐시(LRU)하는 구조로
가야 한다 — ~~지금은 로컬이 전부 갖고 있어야 하는 구조라 할당량이 상한이다.~~
**→ 2026-08-31 v3에서 이 구조로 전환 완료(§4-3).**

## 4-3. v3 — 공용 보관함(서버 정본 + 로컬 LRU 캐시), 2026-08-31

"개인(브라우저 로컬) 보관함 + 수동 백업" 모델을 폐지하고 **서버가 정본인
공용 보관함 하나**로 일원화했다. 서버(`/api/library`) 코드는 그대로다 —
매니페스트는 서버가 내용을 해석하지 않는 blob이라 클라이언트 계약만 바꿨다.

- **비밀번호·연결 절차 없음**(오너 결정): "어떤 환경에서 보든 동일한 스페이스"가
  요구사항이라 보관함의 비번 게이트를 서버·클라이언트 양쪽에서 제거했다.
  `/api/library`의 listfiles·업로드 토큰 발급 모두 무인증이고, 남은 방어선은
  경로 검증(`library/f/`·`library/manifest.json` 외에는 토큰을 안 준다)과
  파일 크기 상한(500MB)뿐이다. **엔드포인트 URL을 아는 사람은 목록 조회·업로드·
  덮어쓰기가 가능**하다(URL은 공개 번들에 들어 있다). 피드백 관리자 조회
  (`/api/admin`)도 2026-09-02 부터 인증이 없다.
- **자동 동기화**: 앱 로드 시 + 보관함 변경(추가/삭제/폴더 정리) 후 2.5초
  디바운스로 자동 동기화. 수동 "동기화" 버튼도 유지. 서버가 잠깐 안 되면
  로컬 보관함으로 계속 쓰고 다음 변경 때 다시 맞춘다.
- **매니페스트 v3** (`LIBRARY_MANIFEST_VERSION = 3`): `deleted: {artworks,
  sections}`(해시/id → 삭제 시각) 필드를 추가해 **삭제가 기기 간에 전파**된다.
  각 항목의 `updatedAt`이 삭제 시각보다 나중이면 "삭제 후 재추가"로 보고
  살린다(그 삭제 기록은 소멸). v2 매니페스트도 그대로 읽힌다.
  로컬 기록은 IndexedDB `tombstones` 스토어(DB_VER 4).
- **목록만 동기화, 본체는 필요할 때**: pull은 파일을 내려받지 않고 메타데이터
  (+서버 URL)만 로컬 목록에 반영한다(`applyManifestToLocal`). 본체(blob)는
  실제 사용 시점(`getArtworkFile`)에 내려받아 캐시한다(사이드바에 ☁ 표시).
- **로컬 LRU 방출**(`pruneBlobCache`): 사용량이 할당량의 60%를 넘으면 서버에
  본체가 있는 항목부터 오래 안 쓴 순서로 blob만 비워 50% 아래로 내린다.
  → **로컬 할당량(≈3GB)이 더 이상 보관함 크기의 상한이 아니다.** 서버는
  Vercel Blob + 커서 페이지네이션이라 수백 장(200장+)도 문제없다.
- 동시 편집: 마지막에 올리는 쪽이 매니페스트를 병합해 쓰므로(pull→merge→push
  가 한 호출 안에서 일어남) 짧은 경합에서 항목이 사라지지 않는다. 항목 단위
  최신자 승.
- blob 정리는 하지 않는다: 삭제된 파일의 blob은 서버에 남는다(내용 주소·추측
  불가 경로). 이력 롤백 가능성을 위해 의도적으로 지우지 않는다.

## 5. 서버 보관 시 마이그레이션 메모
- 아트웍 dedup 키는 이미 파일 해시(SHA-256, http 폴백 FNV) → 서버에서도 그대로
  키로 써 중복 업로드를 자연 제거.
- `sections`는 `{id, name, createdAt, parentId}` 구조(중첩 지원) → JSON 한 덩어리로
  저장하면 됨.
- 원본 라벨은 민감할 수 있으므로 피드백 수집기처럼 **접근 URL 추측 불가
  (addRandomSuffix)** + 비번/인증 게이트를 반드시 유지.
